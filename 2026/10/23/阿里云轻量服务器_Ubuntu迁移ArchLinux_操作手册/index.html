阿里云轻量应用服务器 Ubuntu 迁移 Arch Linux 操作手册

这篇记录一次在阿里云轻量应用服务器上，把正在运行的 Ubuntu 换成 Arch Linux 的过程。适用这台 x86_64、单盘、GPT、UEFI、ext4、DHCP 的机器，整理日期是 2026-10-17。

高风险：这是替换操作系统，不是普通升级。 会中断服务，并可能导致 SSH 失联或无法启动。先完成异地备份，并确认控制台还能连上、能看到启动画面，再进入会改磁盘的步骤。不要把全文复制后一次执行。

4. 风险边界与恢复准备

开始前完成：

  1. 在控制台创建可用的系统盘备份/快照，并核实当前产品的恢复方式；另做异地数据备份。
  2. 单独导出 Docker Compose、环境文件、数据库一致性备份、卷数据、网站配置、证书、SSH 公钥和应用配置。磁盘快照不自动保证数据库一致性。
  3. 验证阿里云远程控制台能实际连接、看到启动画面并输入命令。控制台是输入输出入口，不自动提供独立救援系统。
  4. 确认 TCP 22 入站规则允许管理员访问，并记录公网连接地址。
  5. 保存分区、UUID、路由、EFI 配置到本地电脑；服务器内的唯一副本不算异地备份。
  6. 规划停机窗口，停止业务写入后再制作最终数据备份。

禁止操作：

  • 不对 /dev/vda3 执行 mkfs、wipefs 或 DD；安装源和 ISO 都在该分区内。
  • 不对 /dev/vda2 重新格式化；本次复用现有 EFI。
  • 不在运行中的 Ubuntu 对 / 执行删除或镜像覆盖。
  • 不因 copytoram=y 或根目录为 airootfs 就认定 ISO 已完全脱离系统盘。
  • 不用 umount -l、强制卸载或批量 losetup -D 绕过占用问题。
  • 不将示例 EFI 编号、公网地址或旧 DHCP 租约直接当成新机器参数。

恢复边界：在替换前，旧 Ubuntu 仍可能作为回退入口；替换后，保留 Ubuntu EFI 文件不等于 Ubuntu 仍能启动。必须通过 Live、外部救援或备份恢复。

原对话确认 Live 根为 airootfs。但还必须检查完整依赖链：

也可能看到 squashfs 后端已转到 /run/archiso/copytoram/...，表示数据在内存路径。存在 loop 本身不是错误；关键是 loop 后端是否仍位于 /dev/vda3。 对可疑后端路径用 findmnt -T 实际后端路径 追溯文件系统，不能只搜索 /mnt/target 字样；同一分区可能挂在 /run/archiso/img_dev。

9.1 允许继续的条件

  • Live 根不是 /dev/vda3。
  • 活跃 Live squashfs/overlay 的后端不依赖该分区中的 ISO 或其他文件。
  • /dev/vda3 没有被 archiso 以只读形式继续占用，或已经通过正常卸载完成释放。
  • 所有可能需要的工具已经可用，网络/控制台可工作，内存有余量。

9.2 Live 网络临时恢复

Live 网卡名可能不是 eth0，因为上述 Live 菜单没有设置 net.ifnames=0。先用 ip -br link 识别实际名字，再为实际网卡配置 DHCP、启动 networkd；不要直接照搬网卡名。临时修改 Live 的配置不会自动进入硬盘 Arch。

10. 根文件系统替换：安全修订方案（L）

10.1 为什么不直接照抄原来的 rsync –delete

原记录设置：

源目录位于目标内部。对目标使用 --delete，若安装源保护失效，rsync 会把源当成目标多余内容删除，后续出现文件消失或迁移中断。ISO 也有同样风险。

原记录用 --exclude='/opt/arch-install/***' 等保护目录；标准 rsync 排除规则通常同时影响发送端与接收端删除保护，但保护依赖路径和选项，不是任意情形的保证。不能添加 --delete-excluded，也不能只写发送端隐藏规则就以为接收端安全。详见 rsync 官方手册。

此外，原 -n 模拟没有 -i 或 -v，可能看不到足够的逐项变化；被排除的旧 /dev、/run、/tmp 内容也会留下。仅去掉 --delete 则会残留大量旧 Ubuntu 文件，尤其旧 /bin、/lib 等结构可能与 Arch 的符号链接冲突。

本文改为先在同一 ext4 内隔离旧内容，再 rsync 无删除复制。 这样能避免在嵌套源上运行删除同步；需要足够磁盘空间，并且中途失败后不能直接重启。

10.2 写入前关卡

以下只适用于“尚未替换，旧根仍是 Ubuntu”的机器。已经成功安装 Arch 的机器不要重跑第 10 节。

完成第 9 节的 ISO 释放检查后：

此时目标下不得挂载 EFI 或其他子文件系统。findmnt -R /mnt/target 应只有目标本身。Bootstrap 的 /dev、/sys 等也不能仍有子挂载。若存在，先查清并正常卸载；本文不使用强制卸载。

剩余空间应大于安装源再复制一份所需空间，并留出包缓存、initramfs 和日志余量。原可用空间不能替代此时检查。

18. 相对最初方案的修正

  1. 替换嵌套源 rsync --delete：采用旧文件隔离 + 无删除复制，避免源被接收端删除，旧目录与符号链接结构也先移开。
  2. 模拟同步加可见输出：使用 --dry-run --itemize-changes，不能把“没看到输出”当作删除清单安全。
  3. 严格检查 ISO 依赖链：copytoram 参数和 airootfs 不是分区已释放的证据；loop 是否安全取决于后端位置。
  4. 区分 Live 和 chroot：验证目标实际挂载及 os-release，再配置硬盘 SSH；不把 Live 的 10-archiso.conf 当作目标必然污染。
  5. 恢复配置换行：GRUB、networkd、mirrorlist、sshd 配置各指令单独一行，避免导出文本的一行粘贴错误。
  6. 校验值标注来源：保留原 ISO SHA256，但不把未经独立核实的历史值当作可信发布校验。
  7. 不固化租约/示例编号：IP 和网关继续 DHCP；0007 仅示例；最终 EFI 编号现场取得。
  8. 修正 sudo 编辑方式：用 visudo 或 EDITOR=nano visudo，不使用 EDITOR=visudo visudo。
  9. 不在 chroot 验证服务运行或重启：只配置 enable，退出后从 Live 正常卸载重启，再检查服务 active。
  10. 增加持久启动验收：BootNext 仅一次；确认 BootOrder 并做受控二次启动后再删除安装材料。
